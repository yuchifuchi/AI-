# ローカル完全版（GPUなし・IIS同居・Access）検討

## 0. 結論（3行）

1. **作れます。ただし「AWS版と同じ品質・同じ速さ」にはなりません。** 回答は 1件あたり 40秒〜3分（構成による目安）、日本語の品質は現行の Claude Haiku 4.5 より明確に落ちます。設計書の**図の「意味」をAIに理解させることは、GPUなしでは実質不可能**です。
2. **図については別の抜け道があります。** PDFを解析するのではなく、**元ファイル（.pptx / .docx / .xlsx / .vsdx）を直接読む**と、「どの箱とどの箱が線でつながっているか」がXMLに書いてあるので、AIもGPUもOCRも使わず確実に取れます。これが今回いちばん大きな発見です。
3. **推奨は「ローカル化はやる。ただし『GPUなし』か『IIS1台同居』のどちらか一方を緩める交渉を先にする」。** どちらを緩めても「データを社外に出さない」という本来の目的は1ミリも損なわれません。緩められないなら、4B〜8B級モデル＋文脈圧縮＋非同期UI＋図の意味理解は諦める、という前提でなら成立します。

## 3. GPUなしの現実（性能）

### 3-1. まず「なぜ時間がかかるか」を分けて理解する

AIの回答は2段階で、**それぞれ詰まる場所が違います**。

| 段階 | やること | 何で決まるか |
|---|---|---|
| **prefill（下読み）** | 検索した資料＋質問をまとめて読む | **CPUのコア数と計算力**。コアを増やすと速くなる |
| **生成（decode）** | 答えを1文字ずつ書く | **メモリの帯域（読み出し速度）**。コアを増やしてもほぼ速くならない |

生成速度はこの式でだいたい先に読めます（実測しなくても桁は分かります）。

```
生成 tok/s ≒ 実効メモリ帯域(GB/s) ÷ 1トークンで読むデータ量(GB) × 0.5〜0.8
```

- メモリ2チャネル DDR4-3200 = 理論 51.2 GB/s、実効 35〜40 GB/s
- メモリ8チャネル DDR4-3200 / DDR5 = 理論 205〜307 GB/s、実効はコア数次第で 120〜200 GB/s

つまり**「コア数」より先に「メモリが何チャネル刺さっているか」を見るべき**です。DIMMが1枚しか刺さっていないサーバは実在し、その場合はメモリを足すのが最大の高速化になります。

### 3-2. モデル階層と所要時間

> **前提（これが変わると数値も変わります）**: Q4_K_M量子化 / 入力3,000トークン（参考資料のチャンク数を現行の8→4に絞った場合）/ 出力400トークン（現行の maxTokens=1000 を絞る）/ thinking無効 / 同時実行1件 / n_ubatch=512 / モデルは全量RAM常駐。**すべて目安であり、実機での実測が必要です。**

| 階層 | 例 | ファイル | LLM分のRAM | A: 8コア・2chメモリ | B: 16コア・8chメモリ | 日本語品質の目安 |
|---|---|---|---|---|---|---|
| 4B 密 | Qwen3-4B-Instruct-2507 | 2.5GB | 約4GB | **1.5〜3分** | **40〜70秒** | 要約はできる。仕様の突き合わせは不安定 |
| 8B 密 | Qwen3-8B | 5.0GB | 約6.5GB | 3.5〜6分 | **1〜2分** | 実用ラインの下限 |
| 14B 密 | Qwen3-14B | 9.0GB | 約11GB | 6〜9分（実用外） | 2〜4分 | かなり良い |
| 20B級 MoE | gpt-oss-20b (MXFP4) | 12.1GB | 約13GB | 2〜3.5分 | 45〜90秒 | 速いが日本語はQwen系に劣る |
| 30B-A3B MoE | Qwen3-30B-A3B-Instruct-2507 | 18.6GB | 約20GB | 2〜4分 | **45〜100秒** | オープン系では最上位帯 |

**現行設定のまま（入力5,000トークン・出力1,000トークン）だと、上の表の 2〜2.5倍かかります。**
逆に言えば、**入力を絞る・出力を絞るのが、ハードを1円も足さずにできる最大の高速化**です。

### 3-3. MoE（混合エキスパート）がCPUで有利な理由

「30B-A3B」というモデルは、**中に30億×多数の専門家がいるが、1文字書くたびに3億3千万人分しか呼ばない**という作りです。生成はメモリの読み出し速度で決まるので、「毎回全部読む27B密モデル（16.8GB）」より「毎回2.3GB分しか読まないMoE」のほうが圧倒的に速くなります。

ただし**理論通りにはなりません**。理論では8倍差ですが、専門家ごとの計算が細切れになるため、llama.cpp の実測では**3〜4倍程度**にとどまります。実測アンカーとして、48コア EPYC 9454P（12chDDR5）で Qwen3-30B-A3B が 63.1 tok/s、12コアの2ch機で3B活性MoEが 7.74 tok/s という報告があります。

### 3-4. 同時に何人使えるか（ここが一番の落とし穴）

llama.cpp は1件の質問で**全コアを100%使い切ります**。だから2人同時に質問すると、2人とも約2倍待つだけで、合計の処理量は増えません。`--parallel` を増やしても同じです。

待ち行列の試算（利用者40人・1人1日5問・8時間稼働 = 25問/時）。

| 1件の所要時間 | 稼働率 ρ | 平均待ち時間（M/M/1近似） | 体感の総応答時間 |
|---|---|---|---|
| 90秒（16コア機・30B-A3B） | 0.63 | 約150秒 | **約4分** |
| 43秒（文脈を圧縮した場合） | 0.30 | 約18秒 | **約1分** |
| 180秒（8コア機） | 1.25 | **発散（永遠に終わらない）** | 破綻 |

しかもナレッジ検索は「朝一」「月次締め」「障害発生時」に集中します。**平均で設計すると必ず破綻します。** 対策は3つセットです。

1. ローカルAPI側で**同時実行を1件に直列化**する（キュー）
2. 画面に「あなたは順番待ち 3番目です」と出す
3. 同じ人が連打しても二重に走らせない（単一フライト制御）

## 4. Accessをどう使うか（ベクトル検索の問題）

### 4-1. なぜAccessだけでは検索できないのか

AI検索は「質問を数百個の数字の並び（ベクトル）に変えて、似た数字の並びを持つ文書を探す」という仕組みです。ところが、

- **Accessには「ベクトル」という型がありません。** 数字の並びは CSV の文字列か、バイナリのかたまりとして入れるしかありません。
- **AccessのSQLには「似ている度合いを計算する」機能がありません。** 必ず全部読み出して、アプリ側（＝VBScript）で計算することになります。
- **VBScriptにはバイナリを数値配列に戻す手段が実質ありません**（CopyMemory相当がない）。だからCSV文字列にせざるを得ず、「文字列→数値の変換」が計算そのものより重くなります。

### 4-2. VBScriptで総当たり計算する案がなぜ厳しいか

1万チャンク × 768次元 = **768万回**の掛け算＋足し算が必要です。

| 内訳 | 見積り |
|---|---|
| 内積のループ本体 | 2.0〜5.1秒 |
| 文字列→数値の変換（768万回） | 数十秒規模 |
| Split | 数秒 |
| ADO でのデータ取り出し（1万行） | 数秒 |
| **合計（1回の質問あたり）** | **現実的には30〜120秒** |

同じ計算を Python + numpy でやると **0.48ミリ秒**です（本検証環境での実測）。**約10万倍の差**があります。

さらに悪いことに、
- 現行の Titan Text Embeddings V2 の既定は **1024次元**なので、768次元前提だと計算量は33%増えます。
- 上の数字は「マシンがヒマなとき」の値です。同じマシンでローカルLLMが全コアを使っている最中は、さらに2〜5倍遅くなります。
- Access の **.accdb は1ファイル2GBがハード上限**です。768次元のCSVを Long Text に入れると1行 6.8〜13.5KB なので、**5万チャンクあたりで上限に当たります**。

**結論: Accessにベクトルを入れて VBScript で計算する案は採用しない。**

### 4-3. 現実的な分担

| 層 | 中身 | 置き場所 | 役割 |
|---|---|---|---|
| 原本 | PDF/Word/Excel の実ファイル | `D:\kb\docs\` （**wwwroot の外**） | これが「正」 |
| サイドカー | `{doc_id}.metadata.json` | 原本と同じ場所 | 復旧の「正」 |
| **Access** | documents / chunks の**メタ情報だけ**（id, title, author, category, sensitivity, type, ext, 見出しパス, 画像パス） | `D:\kbdata\kb.accdb` | **管理画面のためだけ**に使う。1行1KB未満なので数十万行でも余裕 |
| ベクトル索引 | 正規化済み float32 の `.npy` + ids.json | `D:\kb\index\` | 再生成できる派生物。バックアップ対象外でよい |
| 本文 | チャンク本文の JSONL | `D:\kb\text\` | Accessに入れると2GBに近づくので外へ |

**ANN索引（faiss / hnswlib）は不要です。** numpy の総当たり内積で、20万チャンク×256次元なら実測3ミリ秒（アイドル時）、LLMがCPUを使っている最中でも中央値125ミリ秒・最大351ミリ秒でした。加えてオフライン環境では、hnswlib は Windows のホイールが配布されておらずMSVCビルドが必要、faiss-cpu はホイールがあるがHNSWの削除ができない、という事情があり、**総当たりのほうが安全で運用も楽**です。

**次元は 1024 → 256 に落とすのが効きます。** メモリも計算時間も1/4になります（Matryoshka対応の埋め込みモデルを選ぶ）。

### 4-4. Accessドライバ（ACE）の注意 ※要確認事項

- **Microsoft Access Database Engine 2016 再頒布可能パッケージは 2025年10月14日にサポート終了済み**です。対応OS表記も Windows Server 2012 R2 までで、Server 2016以降は「入るが正式対応外」です。
- しかも Microsoft 自身が「システムサービスやサーバーサイドのプログラムでの使用は想定していない」と明記しています。今回の構成はまさにこれに該当します。
- **ただし、ASP側はAccessに一切触れません。** kb_lib.asp にDB接続コードは無く、外部通信は ServerXMLHTTP だけです。つまり **IISアプリプールが32bitか64bitかは、Access接続と無関係**です。

ACEが導入できない場合の逃げ道（どれも「Accessを使う」という条件は守れます）。

| 案 | 内容 | 注意 |
|---|---|---|
| A | サーバに Microsoft 365 Apps (C2R) v2009以降が入っていれば、ACEが既に使える可能性 | 版によるので実機確認が必要 |
| B | 32bit ACE + 「Access書き込み専用の小さな32bitプロセス」に分離。LLMは64bitプロセス側 | 32bitプロセスにLLMを載せてはいけない（アドレス空間2〜3GB） |
| C | UCanAccess / Jackcess（純Java）で .accdb を直接読み書き。ACE不要・ビット数非依存 | JREの導入が必要 |
| D | 実体は SQLite にし、Access からは ODBC リンクテーブルで見る | 「Accessの画面で管理する」体験は完全に維持される |

## 5. 図・画像の解析はどうなるか

**3つに分けて考えます。ごちゃまぜにすると判断を誤ります。**

| やりたいこと | GPUなしで | 手段 |
|---|---|---|
| ① 図の中の文字を読む（ベクタPDF） | **できる。しかも高精度** | テキスト抽出だけ。AIもOCRも不要 |
| ② 図の中の文字を読む（スキャン・画面キャプチャ） | **できる。ただし数字は信用できない** | OCR |
| ③ **図の「意味」を理解する**（どの箱がどこにつながるか） | **PDF経由では不安定。元ファイル経由なら確実に取れる** | 下記参照 |
| ④ 図を見て自由に説明させる（VLM） | **実質不可能** | CPUで1ページ約1分〜15分。しかも精度が未検証 |

### 5-1. ③が今回の一番の発見

**PDFを解析するのはやめて、元ファイルを直接読むべきです。**

.pptx / .docx / .xlsx / .vsdx は**中身がZIP + XML**で、標準ライブラリだけで開けます。そして「つながり」がXMLに**明示的に書いてあります**。

| 図の種類 | どこに書いてあるか |
|---|---|
| SmartArt | `diagrams/data1.xml` の `dgm:ptLst`（箱）と `dgm:cxnLst`（接続） |
| 図形のコネクタ | `p:cxnSp` の `a:stCxn` / `a:endCxn`（接続元・接続先の図形ID） |
| Visio | `visio/pages/page*.xml` の `<Connect FromSheet=... ToSheet=.../>` |
| Excelグラフ | `xl/charts/chart*.xml` の `c:ser` / `numCache`（系列名と実数値そのもの） |

実際に検証したところ、同じ構成図で **PDF経由ではつながりが0件**しか取れなかったのに対し、**.pptx を直接読むと接続グラフが曖昧さゼロで確定しました**。

一方、PDF経由のベクタ図解析は**出力元ツールに強く依存**します。検証では、LibreOffice経由で書き出したPDFに「矩形」という描画命令が0個しかなく（箱が塗りの四角形＋角丸の輪郭パスとして出力されていた）、素朴な矩形検出では箱が1つも見つかりませんでした。**「ベクタPDFなら機械的に取れる」は条件付きです。**

> **注意**: 「Office実機でPDFに書き出せばいい」は採れません。Microsoft は KB257757 で**サーバ上での無人Office自動化を非サポート**と明記しており、ライセンス上も、M365ならオンライン認証が必要な点でも「インターネット非接続」と衝突します。

**したがって、最初に調べるべきは「設計書の何%でファイルサーバから元ファイルを回収できるか」です。** ここが5割を切るなら、図の構造化は諦める判断になります（旧形式の .vsd / .doc / .xls はライブラリ支援が乏しいので別枠で数えてください）。

### 5-2. ②OCRについての正直な話

Tesseract の日本語OCRは、**設定と資料の質で結果が桁違いに変わります**。

- `--psm 6` は「ページ全体を1つのかたまりとして読む」指定です。1段組のきれいなページでは劇的に精度が上がりますが、**表や多段組では読み順が壊れます**。設計書には表が多いので、`--psm 3 / 4 / 11 / 12` を含めて選び直す必要があります。
- クリーンな描画では文字誤り率0.4%という値も出ますが、**実際のスキャン紙での独立比較では Tesseract の平均CERが35%、ノイズが乗るとほぼ全滅という報告**もあります。「数%で済む」とは考えないでください。
- **壊れるのは日本語ではなく英数字です。** 検証で `FTPS/990 → FTPS/999`、`02:00 → 2:60`、`タイムアウト10秒 → 16秒`、`HOST → HO0ST` といった誤りが出ました。**利用者が一番聞きたい値が、無言で、もっともらしく壊れます。**
- 対策: OCR由来のチャンクには必ず「この内容はOCRで読み取ったため、数値は原本で確認してください」を付け、AIの回答にもその旨を出す。
- 代替: PaddleOCR(japan) / RapidOCR、または Windows標準の Windows.Media.Ocr（日本語言語パックを追加するだけ、追加インストールゼロ）。なお jpn.traineddata は2017年から再訓練されていないので、「新しいTesseractを待つ」は改善策になりません。
- **評価指標はCERではなく**、「型番・画面ID・エラーコードのキーワード再現率」と「想定質問30問での検索ヒット率」にしてください。助詞に散った15%の誤りは無害で、コードに集中した5%の誤りは致命的です。

### 5-3. ④VLM（図を見て説明させる）について

CPUのみでの所要時間は、**同じマシンでも前提次第で 0.9分〜15.5分/ページと20倍振れます**（解像度キャップ・量子化・出力トークン数で決まる）。今回の用途（図の説明を200〜400トークンで書かせる、解像度は1024相当にキャップ）なら**約1分/ページが目安**です。

ただし、
- 速度以前に、**3B級VLMが日本語の構成図を正しく読める保証がありません**。「遅くて不正確」になる可能性が高いです。
- サーバに常駐させる案は非推奨です。IIS・Access・チャット用LLMと同じコアを奪い合います。

**妥協案（この順に検討）**
1. 元ファイルから構造抽出（§5-1）。CPU時間ほぼゼロ、幻覚ゼロ。
2. 重要な図にだけ**人が1行の説明を書く**。kb_register.asp という人手入力の導線が既にあります。数十人規模なら費用対効果は圧倒的です。
3. どうしてもVLMが要るなら、**別マシンで1回だけバッチ**を回してテキスト化し、その結果だけを持ち込む。社外にデータは出ません。

## 6. IISサーバに同居させる場合の注意（重要）

### 6-1. まず誤解を1つ解いておく

「AIの質問で待たされている間、他の業務ASPも固まるのでは」という心配がありますが、**ASPのセッション直列化が効くのは「同じ人の・同じブラウザの・同じIISアプリケーション内」だけ**です。他の利用者や他業務は巻き込まれません。

本当に共有されて困るのは**アプリケーションプール（w3wp）**です。ここが共通だと、ASPスレッドプールとリサイクルを共有します。**これは「専用のIISアプリケーション＋専用のアプリケーションプール」に分ければ遮断できます。別マシン一択にはなりません。**

まず `appcmd list app` / `appcmd list apppool` で現状を確認してください（web.config に `<asp>` ブロックがあるので、tacit2 は既に独立したIISアプリになっている可能性があります）。

### 6-2. ただし、アプリプールを分けてもCPUは分けられない

これが同居の本質的な問題です。

- LLMは全コアを100%使い、さらに**メモリの帯域とL3キャッシュを洗い流します**。
- **プロセス優先度もCPUアフィニティも、メモリ帯域とL3は分割できません。**
- したがって、対策をすべて入れても**他の業務ASPは1〜4割遅くなります**（対策なしなら10〜100倍遅くなる）。

### 6-3. 緩和策（4点セット・全部入れる）

| 対策 | やり方 |
|---|---|
| ① スレッド数を絞る | `llama-server --threads <物理コア数-2>`（16コアなら14、8コアなら6）。ハイパースレッディングまで使うと**逆に約20%遅くなる**実測あり |
| ② コアを固定する | `--cpu-range` / `--cpu-mask`、またはWindowsのプロセッサアフィニティ |
| ③ 優先度を下げる | BelowNormal（NSSM の `AppPriority`、または `--prio -1`） |
| ④ 同時1件に固定 | `-np 1` ＋ ローカルAPI側のキュー |

「絶対にここまで」というハード上限が要る場合は、**Job Object の CPU レート制御**が使えます（Windows 8 / Server 2012 以降。**procgov** という既製ツールがあるので自作は不要）。IISアプリプール側の `cpuLimit action=Throttle` は IIS 8.0（Server 2012）以降ですが、**別プロセスのLLMには効きません**。

> WSRM（Windows System Resource Manager）は **Server 2012 R2 で削除済み**です。しかも「システム全体のCPU負荷が70%を超えたときだけ働く動的配分」なので、今回の用途には元々合いません。OSバージョンによる設計分岐は不要です。

### 6-4. タイムアウトの本当の壁（ここは正確に理解してください）

よくある誤解: 「`kb_lib.asp:103` の `90000` が応答全体の締切だから、ここを大きくすれば通る」

**これは違います。** `setTimeouts` の第4引数は Microsoft のドキュメント上「**1パケットの受信を待つ時間**」であり、応答全体の締切ではありません。

**本当の90秒の壁は、WinHTTP の `RECEIVE_RESPONSE_TIMEOUT`（全応答ヘッダを受信するまでの上限、既定90秒）です。しかもこれは MSXML からは設定できません。**

対処は2通りあります。

| 方式 | 内容 | 評価 |
|---|---|---|
| **チャンク応答**（ASP無改造で通る） | ローカルAPIが受信直後に「200 + ヘッダ」を即返し、生成中は数秒おきに空白を1バイト流し、最後にJSON本体を出す。ASPの `JsonStr` はキーを文字列検索しているだけなので、本体前の空白は完全に無害 | 90秒の壁は消える。ただし**逐次表示にはならない**（`responseBody` を送信完了後に一括で読むため）。総時間の上限が無くなるのでASPスレッドが滞留する危険もある |
| **非同期ジョブ + ポーリング**（推奨） | kb_ask.asp?ajax=1 が質問を投げて即 job_id を返し、ブラウザが1.5〜2秒おきに結果を取りに行く | ScriptTimeout・スレッド枯渇・F5二重実行・セッション直列化が**全部同時に解決**する。文字が流れ出す表示にもできる |

**さらに `Server.ScriptTimeout = 120` の壁も残ります**（kb_ask.asp:7 ほか5画面）。同期COM呼び出し中にこれが実際に発火するかは環境差があり、**未確定**です（発火しなければスレッドが解放されず滞留する、という別の問題になります）。

### 6-5. プロキシ設定の罠

`kb_lib.asp:105` は `If Len(RELAY_PROXY & "") > 0 Then http.setProxy 2, RELAY_PROXY, ""` です。

- **`RELAY_PROXY` を空にすると `setProxy` が呼ばれません。** これは「プロキシ無し」ではなく「**マシン全体のWinHTTP設定を継承**」という意味です。`netsh winhttp` にプロキシが設定されていれば、127.0.0.1宛でもプロキシに飛びます。
- **`<local>` はバイパスリストとして効きません。** `<local>` は「ピリオドを含まないホスト名」だけが対象で、`127.0.0.1` はピリオドを含むため対象外です。
- **確実な直し方**: `http.setProxy 1`（SXH_PROXY_SET_DIRECT）を無条件で呼ぶ1行に変える。RELAY_PROXY という設定項目自体を廃止するのが筋です。
- **URLは `localhost` ではなく `127.0.0.1` と直書き**してください。localhost だとWindowsは `::1`（IPv6）を先に試すため、LLMがIPv4のみ待受だと毎回1秒近く無駄になります。

### 6-6. その他の同居時の注意

- **Webガーデン禁止**: アプリプールの `maxProcesses` は必ず1。Session に会話履歴・ログイン状態・CSRFトークンを持っているので、2以上にすると全部壊れます。
- **定期リサイクルを止める**: 既定の1740分ローリングでw3wpが再生成されると、会話履歴とログインが飛びます。深夜固定時刻（specificTime）に変更。
- **ウイルス対策の除外設定**: モデルディレクトリ（GGUF 18GB）、索引、.accdb、llama-server.exe、w3wp.exe を除外しないと、モデルロードに数分かかったりCPUを恒常的に食われたりします。
- **RAM不足は最悪の形で出ます**: GGUFはmmapで読まれるため、メモリが逼迫するとページアウトが起きて「普段60秒の質問がたまに10分かかる」という再現困難な障害になります。`--mlock`（サービスアカウントに「メモリ内のページのロック」権限が必要）か、素直にRAMを積む。

### 6-7. 同居してよい条件（全部そろったときだけ）

1. そのIISサーバが**このナレッジシステム専用**で、他の基幹業務ASPが載っていない
2. **物理16コア / RAM 48GB以上**に増強できる（あるいは4B級モデルで妥協する）
3. 夜間バッチと時間帯を分けられる
4. §6-3 の4点セットを必ず入れる

**1つでも欠けるなら、別マシンにしてください。**

## 8. セキュリティはどう変わるか

### なくなるリスク

| 項目 | 内容 |
|---|---|
| 社外へのデータ送信 | S3・Bedrock・OpenSearch にデータが一切行かなくなる。これが今回の目的そのもの |
| Function URL の露出 | インターネット上に口が開いている状態が消える |
| X-Relay-Key 漏洩による外部からの悪用 | 外から到達できなくなる |
| Lambda の6MB / MAX_FILE_BYTES 5MB 制限 | 消える。21MB級のファイルもそのまま扱える |

### 新たに自分で守る必要が出るもの

| 項目 | やること |
|---|---|
| **0.0.0.0 バインド事故** | ローカル化で**最も現実的な漏洩経路**。動作確認で `--host 0.0.0.0` にしてそのまま本番化すると、社内LANの誰でも認証なしで全文書を引き出せる。**必ず127.0.0.1のみ** |
| **「localhostだから認証不要」は誤り** | 同じサーバにログオンできる人、同居する他のASPアプリ、他のバッチからは到達できる。**X-Relay-Key / X-Admin-Key は値を変えて維持** |
| **監査ログ** | CloudWatch の構造化ログ（_audit）が消える。ファイル（JSON Lines・日次ローテーション）＋ Accessのログテーブルの両方へ確実に出す |
| **「誰が消したか」** | 共有パスワード認証のままだと特定できない。IIS統合認証の `LOGON_USER`（既に `X-Relay-User` として送っている）を必ず記録する |
| **バックアップ** | S3の高耐久性が消え、壊れやすい単一ファイル（.accdb）に集約される。robocopy で別筐体へ毎日世代コピー（14〜30世代）＋週次でシステム全体。**四半期に1回はリストア訓練**（訓練していないバックアップは無いのと同じ） |
| **原本ファイルの置き場所** | wwwroot配下に置くとURLを知っていれば無認証でダウンロードできる。**必ずwwwroot外**に置き、ASP経由で認可付き配信 |
| **パスの検証（Windows特有）** | 現行の staging キー検証はS3前提。Windowsではバックスラッシュ、ドライブレター（C:）、UNCパス、予約デバイス名（CON/NUL/PRN/AUX/COM1）、代替データストリーム（file.txt:hidden）も塞ぐ必要がある |
| **パッチが当たらなくなる** | オフライン化の最大の長期リスク。WSUS またはオフライン更新の手順を**最初に**決めておく |
| **モデルファイルの持ち込み** | GGUF と safetensors に限定（.bin/.pt/.pkl は読み込みだけで任意コード実行の危険）。SHA256 で取得元と一致確認 |
| **BitLockerを過信しない** | 守るのは盗難・廃棄時だけ。稼働中サーバへの侵入やLAN経由の不正アクセスには一切効かない。実際に効くのはNTFSのACLと最小権限のサービスアカウント |

## 9. 段取り（やるならこの順）

### Step 0: 現状把握（0.5日）— これをやらずに機器を発注しない

| 調べること | コマンド・方法 |
|---|---|
| メモリが何チャネル刺さっているか | `wmic memorychip get BankLabel,Speed,ConfiguredClockSpeed,Capacity` |
| 物理コア数・AVX-512/AMXの有無 | `systeminfo`、CPU型番から確認 |
| 空きRAM | タスクマネージャ |
| IISアプリ・アプリプールの構成 | `appcmd list app` / `appcmd list apppool` / `appcmd list wp` |
| Officeの有無とビット数・C2Rバージョン | `HKLM\SOFTWARE\Microsoft\Office\ClickToRun\Configuration` の Platform |
| WinHTTPのプロキシ設定 | `netsh winhttp show proxy` |

**判断**: メモリが1〜2チャネルしか無ければ、まずDIMM増設を検討（他のどの最適化より効く）。

### Step 1: 素材の全数棚卸し（2〜3日）— サンプルではなく全部数える

S3に全原本があるので、PyMuPDF等でのスクリプト走査は数百ファイルでも数分で終わります。20〜30本のサンプルでは信頼区間が±18ポイントも開いて判断に使えません。

数えるもの: ①**元ファイル（.pptx/.docx/.xlsx/.vsdx）がファイルサーバから回収できる割合** ②PDFの `/Producer` `/Creator`（出力元ツール別に層別する）③テキスト層の有無 ④不可視テキスト層（複合機のサーチャブルPDF）の有無 ⑤ページ単位での「本文/表/ラスタ画面キャプチャ」の内訳。

**判断**: 元ファイル回収率が5割未満なら、**図の構造化は諦める**（OCRによる文字拾いだけにする）。

### Step 2: 速度の実測（2〜3日）

```
llama-bench -m <model>.gguf -p 3072 -n 400 -d 2048,4096 -t 4,6,8,12,14 -r 3
```

- `-d`（KVキャッシュの深さ）を必ず付ける。既定の `-d 0` は最良ケースしか測らず、実運用より速く出ます。
- prefill と生成を**分けて**記録する。
- Q4_K_M / Q6_K / Q8_0 の3通りを比較（AMX搭載Xeonなら、モデルロード時のログに `AMX model buffer size` が出るかを先に確認）。
- **IIS/Accessに負荷をかけた状態でも測る**。アイドル機の値は上限であって設計値ではありません。
- 同時2件の劣化も測る（llama-bench では測れないので llama-server に実負荷をかける）。

**判断**: 入力3,000 / 出力400 で3分を超えるなら、モデル階層を1段落とす。4B級でも3分を超えるなら**同居は断念**して別マシンかGPUへ。

### Step 3: 品質のA/B評価（1週間）— ここが本当の関門

実際に社内で出た質問30問で、現行のAWS版（Claude Haiku 4.5）とローカル候補を比べます。

- 指標: ①答えが正しいか ②出典が正しいか ③嘘をついていないか
- **モデルは1段ずつ上げる**: 4B → 8B → 14B → 20B級MoE → 30B-A3B。「4Bがダメだから30B-A3B」という飛び方はしない。14B級で足りればRAMは16GBのままで済みます。
- 同時に**検索側の品質**も測る。Bedrock KB + Titan からローカル埋め込みへの置き換えは、**生成モデルの差し替えより大きな品質リスク**です。どんなに良いLLMでも、検索が外れていれば救えません。

**判断**: どの階層でも許容できなければ、**ローカル化は中止するかGPUを入れる**。低品質な回答は「AIは使えない」という評価に直結し、システムごと使われなくなります。

### Step 4: ローカルAPI実装 + 契約テスト（2〜3週間）

`action=ask / register / register_bulk / admin(list,get,edit,delete) / staging(list,register,discard)` の**10ケースのゴールデンテスト**を先に書きます。「同じJSONをAWS版とローカル版に投げて、キー集合・キー順・TSVの列数と列順・エラーコードの綴りが一致するか」を機械的に検証。

**特に注意する3点**
1. JSONは `ensure_ascii=False` 相当で出す（非ASCIIを `\uXXXX` にすると、ASP側のパーサがサロゲートペア非対応のため絵文字や一部漢字が壊れる）。
2. `"ok"` を必ず**先頭のキー**にする（ASPは「最初に一致したキー」を拾う実装）。
3. TSVの列数がずれても**ASPは例外を出さず、表がずれたまま描画されます**。タブ・CR・LFを半角空白に置換する `_san` 処理まで含めて再現。

### Step 5: 並行稼働（1ヶ月）

`kb_config.asp` の1行差し替えで切り替えられるようにしておき、同じ質問を両方に投げて比較。切り戻しは約1分（ASPファイルの更新はアプリプールを再起動しないのでセッションも維持される。**web.config は触らない**）。

### Step 6: 切替

**切戻し手順に「ローカル → S3 への再エクスポート」を必ず含めてください。** 含めないと、切り戻した瞬間に並行稼働中に登録された数日分のナレッジが消えます。

### 担当者への率直な推奨

**「GPUなし」と「IIS1台同居」の2つは、目的（データを社外に出さない）とは無関係な手段の制約です。** どちらか一方を緩めるだけで、応答が3分→10秒になり、他業務への影響が消え、将来の「図を読ませる」も現実的になります。上長への説明では、**「完全ローカルは絶対に守ります。その代わり、GPUを1枚（10〜25万円）か、既存の仮想基盤にVMを1台（追加ハード費0円）ください」**という形で交渉するのが最も効きます。

どうしても両方守る必要があるなら、**まず Step 0〜3 だけを2週間で回してください。** 実機のメモリチャネル数と、社内の実際の質問30問での品質評価。この2つの結果が出るまでは、機器の発注も実装の着手もしないことをお勧めします。特に Step 3 の品質評価でつまずいたら、そこで止めるのが正しい判断です。
