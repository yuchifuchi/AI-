# 想定問答集 ── セキュリティ・仕様について聞かれたら（技術根拠つき）

> 用途：上長・監査・情シス等から「このシステムは大丈夫なのか」と質問（詰問）されたときの回答集。
> 各問答は「**結論1行 → 根拠（技術） → その場で見せられる証拠**」の順。
> 言い切ってよい表現と、言い切ってはいけない表現を分けています（信頼を守るため）。

---

## 0. まず全体像（30秒で説明する版）

> 「社内の設計書やマニュアルを、**ログインした職員だけ**がAIに質問できるシステムです。
> データは**暗号化した非公開のAWS領域**にあり、経路は**4つの関門**（画面ログイン → 拠点IP制限 → 秘密鍵 → 管理鍵）で守っています。
> 外部の人がURLを知っても、**データは一切返りません**。」

```
[職員PC] --①ログイン--> [munu] --②IP制限+③秘密ヘッダ(TLS暗号化)--> [Lambda] --最小権限--> [非公開S3(KMS暗号化)/Bedrock]
```

| 関門 | 中身 | 破られたときの応答 |
|---|---|---|
| ① 画面ログイン | ACCESS_PASSWORD／ADMIN_PASSWORD | ログイン画面から進めない |
| ② 送信元IP制限 | mintの出口IP以外は拒否（ALLOWED_IPS） | `403 forbidden` |
| ③ 秘密鍵ヘッダ | X-Relay-Key（32桁超・定数時間比較） | `401 unauthorized` |
| ④ 管理鍵 | X-Admin-Key（編集・削除・一括投入のみ） | `403 admin_forbidden` |

## 1.「URLを叩かれたら」系の質問

### Q1. システムのURL（AWSの窓口）が外部に漏れたら、情報を抜かれるのでは？

**A. 抜かれません。URLだけでは何のデータも返らない設計です。**

根拠（すべて実装済み・実機確認済み）：
1. **ブラウザで開いても何も出ない**：この窓口はPOST専用。ブラウザのアクセス（GET）は即 `405 method_not_allowed`。画面もデータも存在しません。
2. **mintの外からは全部拒否**：送信元IPがmintの出口IP以外なら、正しい形式のリクエストでも `403 forbidden`。この判定はAWS側（Lambda）で行うため、偽装できるのはIPヘッダではなく実際の接続元IPであり、なりすましは実質不可能です。
3. **鍵がなければ拒否**：仮にmint内からでも、32桁超の秘密鍵（X-Relay-Key）が一致しない限り `401 unauthorized`。
4. **拒否は全て監査ログに記録**：`deny_ip` / `deny_key` として、時刻・送信元IP付きでCloudWatchに残ります（＝攻撃されたら気づけます）。

> 🎤 **その場デモ**（質問者の前でスマホのテザリング等・社外回線から）：
> ```
> curl -X POST "https://＜窓口URL＞" -H "Content-Type: application/json" -d "{}"
> → {"ok":false,"error":"forbidden"}   （403。何のデータも返らない）
> ```
> ブラウザで同URLを開く → `{"ok":false,"error":"method_not_allowed"}`（405）。

### Q2.「どんなURLを叩いてもつながらない」と言い切っていい？

**A. そのままの言い切りは避け、正確にこう言ってください：**

> ✅ 正確な言い方：「**URL自体には到達できますが、外部からは全リクエストが 403／401／405 で拒否され、データは1バイトも返りません。**」
> ❌ 避ける言い方：「つながらない」（→ 詳しい人に `curl` されると"応答はある"ため、言葉尻を取られます）

これは弱点ではありません。**銀行の扉に例えると「扉は見えるが、鍵と身元がないと絶対に開かない」状態**です。「扉が見えること」と「中に入れること」は別です。

### Q3. S3（データの保存場所）に直接アクセスされたら？

**A. 直接アクセスの経路が存在しません。**
- バケットは **Block Public Access 4項目すべてON**（AWSが公開設定自体を禁止する状態）。
- 匿名アクセス・署名付きURL・公開ポリシーは**一切なし**。旧方式にあった公開バケットは**全廃済み**。
- 読み書きできるのは、**IAMで許可された2つのプログラム**（LambdaとBedrock KB）だけ。人間のアカウントにも直接権限を配っていません。
- さらに中身は **KMS（顧客管理鍵）で暗号化**。仮に何らかの方法でファイルを取得できても、鍵がなければ復号できません。

### Q4. 通信を盗聴されたら？

**A. 経路はTLSで暗号化されており、盗聴では読めません。**
- munu→AWS：**TLS（HTTPS）で全暗号化**。秘密鍵はURLではなく**ヘッダ**で送るため、プロキシログ・アクセスログ・ブラウザ履歴に残りません。
- 職員PC→munu（社内LAN）：現在HTTPSへの切替を進めています（証明書手配中）。**完了までの間、この区間は社内ネットワーク内に閉じており、外部からの盗聴経路はありません**（盗聴できるとすれば社内LANに物理的に侵入されている状態で、それはこのシステム固有の問題ではありません）。

### Q5. 鍵を総当たりで破られない？

**A. 現実的に不可能です。**
- 鍵は**32文字以上のランダム英数字（128ビット超の空間）**。総当たりは宇宙年齢オーダーの時間が必要です。
- 比較は**定数時間比較（hmac.compare_digest）**：応答時間の差から1文字ずつ推測する「タイミング攻撃」も成立しません。
- 試行はすべて `deny_key` として**記録**され、そもそも**mint外からは鍵の試行にすら到達できません**（IP制限が先）。
- Lambdaの**同時実行数を5に制限**しており、高速な大量試行は物理的にできません。
- 鍵は**定期ローテーション**運用（台帳に記録）。

## 2.「AWS・AIに預けて大丈夫か」系の質問

### Q6. 業務情報をAWS（クラウド）に置いて大丈夫なのか？

**A. 国内リージョン・暗号化・最小権限で管理しています。**
- 保存先は**国内リージョン（大阪 ap-northeast-3）**。データは国外に出ません。
- 保存時は**S3のKMS暗号化（顧客管理鍵）**＋伝送時はTLS。鍵は当方のAWSアカウント内で管理。
- AWSは政府の**ISMAP（政府情報システムのためのセキュリティ評価制度）に登録**されたクラウドサービスであり、政府機関での利用実績が広くあります。
- 万一の誤削除にも**バージョニング**で復元可能。操作履歴は**CloudTrail**に記録。
- ※「クラウドに置くこと自体の可否」は技術ではなくデータ取扱い方針の問題なので、**方針の確認は別途上長判断**としてください（→Q13）。

### Q7. AIに入れた情報が「学習」されて、他社への回答に出てしまわないか？

**A. 出ません。Bedrockは入力を学習に使いません。**
- Amazon Bedrock は、**顧客の入力・出力をモデルの学習に使用せず、モデル提供元（Anthropic等）とも共有しない**契約・仕様です。
- モデルは**AWSの中で動いており**、質問や文書が外部のAI会社のサーバーに送られることはありません。
- 通信経路も「munu→AWS」の1本だけで、**Web検索などの外向き通信は実装していません**（コード上、外部に出る経路がない）。

## 3.「内部の使われ方」系の質問

### Q8. 職員なら誰でも見られるのか？

**A. いいえ。ログインした担当者だけです。**
- 質問・登録画面は**アクセスパスワード**、管理画面（編集・削除・一括投入）は**別の管理パスワード**が必要。
- 機微な内容がブラウザやプロキシに残らないよう、全画面で**キャッシュ禁止ヘッダ（no-store）**を送出。
- パスワードは異動・退職時に**ローテーション**します（台帳で管理）。

### Q9. 管理画面を突破されたら、全部消される・書き換えられるのでは？

**A. 画面突破だけでは実行できず、消えても戻せます。**
- 編集・削除・一括投入は、画面のログインとは**別に、AWS側で第2の鍵（X-Admin-Key）を検証**してから実行します。画面を突破しても鍵がなければ動きません（＝「見せかけの認可」ではない）。
- 全データは**S3バージョニング**で保護しており、削除・上書きされても**前の版に復元できます**。
- 操作は**CloudTrail（S3の読み書き）とCloudWatch（誰が・いつ・何を）**に記録され、追跡できます。

### Q10. 誰が何をしたか、後から追えるのか？

**A. 追えます。二重に記録しています。**
- **アプリの監査ログ（CloudWatch）**：登録・質問・管理操作・全拒否イベントを、操作者（Windowsログオン名）と送信元IP付きの構造化ログで記録。
- **AWSの証跡（CloudTrail）**：保存領域（S3）への読み書きをAWS基盤側でも記録。
- なお**質問文の本文と回答は記録しません**（長さのみ）。職員の質問内容という機微情報をログに残さないための設計です。

### Q11. AIに見せたくない文書が、回答に出てしまわないか？

**A. 2つの仕組みで防ぎます。**
1. **原則**：AIに見せてはいけない情報は**そもそも登録しない**運用ルール。
2. **例外の逃げ道**：登録後でも、管理画面で文書ごとに**「AIの回答に使わない」**へ切替可能（AIの検索結果から**コードで除外**され、除外した事実も監査ログに残ります）。

## 4.「運用・コスト・正直なところ」系の質問

### Q12. 暴走して高額請求になったり、攻撃で落ちたりしない？

**A. 上限を物理的に固定しています。**
- Lambdaの**同時実行数を5に制限**（大量リクエストでも同時に5件しか処理されない＝コスト・負荷の上限が固定）。
- 処理は**30秒でタイムアウト**。
- （推奨追加：AWS Budgetsで請求アラート。設定手順はマニュアル03参照。）

### Q13.（正直質問）残っているリスクは何か？

**A. 次の4点は把握済みで、それぞれ対応方針があります。「未対策の重大リスク」はありません。**

| 残リスク | 現状の緩和 | 恒久対応 |
|---|---|---|
| 社内LAN区間が平文HTTP | 社内に閉じた区間。外部からの盗聴経路なし | **HTTPS化**（証明書手配中） |
| パスワードが共有制 | ログイン＋IP制限＋機微はAI非公開切替 | 将来**AD認証（本人単位）**へ拡張（Phase 2） |
| 窓口URLが公開エンドポイント | IP制限＋鍵＋監査ログで実質到達不能 | 必要なら**VPN/専用線化**（要投資判断） |
| 第三者のセキュリティ監査が未実施 | 診断指摘は対策済み・設計書と対応表を整備 | 必要に応じ**外部診断**を実施 |

> 上長への締めの一言（推奨）：
> 「**セキュリティ診断で指摘された重大リスクは構造的に解消済み。残る4点は把握のうえ緩和策を講じており、恒久対応の計画があります。『リスクゼロ』とは申しませんが、『未対策の重大リスクはない』状態です。**」

### Q14.「絶対に漏れない」と言い切っていいか？

**A. ダメです。次の言い方にしてください（これが一番強い）。**
- ❌「絶対に漏れません」→ 世の中に存在しない保証。一度でも綻ぶと全信頼を失います。
- ✅「**外部からの既知の侵入経路はすべて塞ぎ、各経路で拒否・記録されることを実機で確認済みです。残るリスクも把握し、対応計画があります。**」

## 5. その場で見せられる「証拠」一覧

| 見せるもの | 場所 | 何の証拠 |
|---|---|---|
| `403 forbidden` の実演 | 社外回線から curl（Q1のコマンド） | 外部から到達不能 |
| `deny_ip` / `deny_key` ログ | CloudWatch → /aws/lambda/munu-kb-routeb | 拒否が記録される |
| Block Public Access = ON | S3 → バケット → アクセス許可 | 公開不能設定 |
| 既定の暗号化 = SSE-KMS | S3 → バケット → プロパティ | 保存時暗号化 |
| バージョニング = 有効 | 同上 | 削除からの復元力 |
| CloudTrail 証跡 | CloudTrail → munu-kb-trail | 読み書きの記録 |
| ログイン画面 | kb_ask.asp を開く | 無認証で使えない |
| 診断→対策の対応表 | `docs/security_summary.md` | 指摘事項の消し込み |
