# 01 AWS設定マニュアル（Route B の窓口を作る）

このマニュアルで、**鍵つきの窓口**（Lambda ＋ Function URL）を AWS に作ります。
既存のナレッジベース（KB）やKBバケットは**そのまま再利用**します（作り直しません）。

> 所要：60〜90分。あわてず、1ステップずつ「✅ こうなれば成功」を確認しながら進めてください。
> 迷ったら止めて、`05_verify_troubleshoot.md` を見る。

---

## 事前チェック（この3つが揃ってから始める）

- [ ] AWSコンソールにログインできる（画面右上のアカウントが `262504054116`）。
- [ ] 画面右上のリージョンが **「東京 ap-northeast-1」**。違ったら切り替える。
- [ ] `00_はじめに` で作った **RELAY_KEY** と **ADMIN_OP_KEY**（32桁以上・別々の値）を手元に用意。

---

## ステップ1. Lambda関数を新規作成する

「窓口の中の人」になるプログラムの入れ物を作ります。

1. コンソール上部の検索窓に **`Lambda`** と入力 → 「Lambda」をクリック。
2. 左メニュー「関数」→ 右上 **［関数の作成］** をクリック。
3. **「一から作成」** を選ぶ。
4. 次を入力：
   - 関数名：**`munu-kb-routeb`**
   - ランタイム：**Python 3.12**（無ければ 3.11 でも可）
   - アーキテクチャ：`x86_64`（既定のまま）
5. 「デフォルトの実行ロールの変更」を開き、**「基本的なLambdaアクセス権限で新しいロールを作成」** を選択（あとで権限を足します）。
6. 右下 **［関数の作成］** をクリック。

✅ こうなれば成功：`munu-kb-routeb` の管理画面が開き、上部に緑色の「正常に作成しました」が出る。

## ステップ1.5. KBバケットのバージョニングをON（削除を元に戻せるように）★必須

管理画面の「削除」は、バージョニングOFFだと**復元できません**。先にONにしておきます（Route Bでも必須。新規構築でも実施）。

1. コンソール検索窓に **`S3`** → S3を開く。
2. バケット一覧から、**`munu-tacit-kb-` で始まるバケット**（＝KBバケット）をクリック。
   - 名前が分からない場合はこれが「KBバケットの実名」です。**このあと何度も使う**のでメモしておく。
3. **「プロパティ」タブ → 「バケットのバージョニング」→［編集］→「有効にする」→ 保存**。

✅ こうなれば成功：プロパティに「バージョニング：有効」。KBバケットの実名も控えられた。

## ステップ2. コードを貼り付ける

1. `munu-kb-routeb` の画面で **「コード」タブ** を開く。
2. 左のファイル一覧で **`lambda_function.py`** をダブルクリックして開く。
3. 中身を**すべて削除**して、このリポジトリの **`aws/lambda_routeb.py`** の中身を**全部コピペ**する。
4. 画面上の **［Deploy］**（デプロイ）ボタンを押す。

> ⚠️ ハンドラ名の確認：Lambda は既定で「`lambda_function.lambda_handler` を呼ぶ」設定です。
> 貼り付け先ファイル名が `lambda_function.py` で、コード内の関数名が `lambda_handler`（そのままでOK）なら、設定変更は不要です。
> もしファイル名を変えた場合は、「設定 → 一般設定 → ハンドラ」を `ファイル名.lambda_handler` に合わせてください。

✅ こうなれば成功：［Deploy］後に「正常に更新されました」と出る。赤い構文エラーが出ていない。

## ステップ3. 環境変数を入れる（窓口の設定値）

`aws/lambda_env.example.json` を見本に、実際の値を入れます。

1. **「設定」タブ → 左「環境変数」→［編集］** を開く。
2. **［環境変数を追加］** を押しながら、次を1行ずつ入れる（キー＝値）：

| キー | 値（例／実値に置換） | 必須 |
|---|---|---|
| `KB_ID` | `HA7C6GUZYZ` | ★ |
| `DATA_SOURCE_ID` | （引き継ぎ資料のデータソースID） | ★ |
| `KB_BUCKET` | `munu-tacit-kb-______`（実名） | ★ |
| `MODEL_ARN` | `arn:aws:bedrock:ap-northeast-1:262504054116:inference-profile/jp.anthropic.claude-haiku-4-5-20251001-v1:0` | ★ |
| `RELAY_KEY` | （用意した32桁以上の合鍵①） | ★ |
| `ADMIN_OP_KEY` | （用意した32桁以上の合鍵②・①とは別） | ★ |
| `KB_PREFIX` | `tacit` | 任意 |
| `NUM_RESULTS` | `20` | 任意 |
| `CONTEXT_CHUNKS` | `8` | 任意 |
| `ALLOWED_IPS` | **最初は空**（テスト後に会社の公開IP `___.___.___.___/32` を入れる） | 任意 |
| `MAX_SENSITIVITY` | `mid` | 任意 |

> 🔎 **`DATA_SOURCE_ID` の調べ方**（値が手元に無いとき）：コンソール検索で **`Bedrock`** →
> 左「ナレッジベース」→ **`munu-tacit-kb`** を開く → 「データソース」欄の **`munu-docs`** をクリック →
> 表示される **「データソースID」をコピー**。これが `DATA_SOURCE_ID` です。
> 🔎 **`KB_BUCKET`（実名）** は、ステップ1.5で控えた `munu-tacit-kb-…` のバケット名です（S3で確認可）。
> ※`DATA_SOURCE_ID` と `KB_BUCKET` は**必須**。空のままだとLambdaが起動時エラーで全リクエスト失敗します。

3. **［保存］** を押す。

> 💡 **`ALLOWED_IPS` は最初は空**にしておきます。理由：テストのとき、あなたのPCやAWSの画面から窓口を叩くと、
> 会社IP以外なので弾かれてしまうためです。munuからの動作が確認できたら、最後に会社の公開IP（OFFICE_IP）を入れて多層防御にします。

✅ こうなれば成功：環境変数の一覧に、上の必須6件（★＝KB_ID/DATA_SOURCE_ID/KB_BUCKET/MODEL_ARN/RELAY_KEY/ADMIN_OP_KEY）が表示されている。

## ステップ4. 実行ロールに権限を足す（触ってよい範囲を決める）

Lambda が「KBバケット・Bedrock・ログ」だけを触れるよう、最小限の許可を与えます。

1. **「設定」タブ → 左「アクセス権限」** を開く。
2. 「実行ロール」の下にあるロール名（`munu-kb-routeb-role-xxxx`）の**リンクをクリック**（IAMの画面が別タブで開く）。
3. IAMのロール画面で **「許可を追加」→「インラインポリシーを作成」** をクリック。
4. **「JSON」タブ** をクリックし、既存の内容を消して、このリポジトリの **`aws/lambda_iam_policy_routeb.json`** を貼り付ける。
5. 貼り付けた中の**プレースホルダを実値に置換**する（下の表）：

| 置換前 | 置換後 |
|---|---|
| `KB_BUCKET_NAME` | あなたのKBバケット名（例 `munu-tacit-kb-abcd`） |
| `ACCOUNT_ID` | `262504054116` |
| `KB_ID` | `HA7C6GUZYZ` |

> 置換は**すべての出現箇所**をやること（エディタの「すべて置換」が便利）。`KB_BUCKET_NAME` は2か所、**`KB_ID` は2か所**、`ACCOUNT_ID` は複数あります。
> ⚠️ `KB_ID` を置換し忘れると `bedrock:Retrieve`/取り込みが `AccessDenied` になり、質問が `internal_error` になります。

6. 右下 **［次へ］** → ポリシー名に **`munu-kb-routeb-inline`** と入れて **［ポリシーの作成］**。

✅ こうなれば成功：ロールの「許可ポリシー」に `munu-kb-routeb-inline` が追加される。

> ❓ もしこの後のテストで `AccessDenied` が出たら、ここのARNの綴り違い・`/*` の付け忘れが原因No.1です（`05` のトラブル表参照）。

## ステップ5. タイムアウトとメモリ、コスト上限

1. **「設定」タブ → 左「一般設定」→［編集］**。
2. 次に変更：
   - **タイムアウト：0分 30秒**（AIの生成に少し時間がかかるため。長すぎると料金増なので30秒目安）
   - **メモリ：256 MB**（既定128でも動くが少し余裕を持たせる）
3. **［保存］**。
4. （推奨・コスト暴走の保険）**「設定」タブ → 左「同時実行」→［編集］** →
   **「予約された同時実行数」を `5`** にして保存。
   - 意味：万一大量に呼ばれても同時に5個までしか動かず、暴走を物理的に止められます。10人利用なら5で十分。

✅ こうなれば成功：一般設定にタイムアウト「30秒」、メモリ「256MB」が表示される。

---

## ステップ6. Function URL（窓口の住所）を作る

1. **「設定」タブ → 左「関数URL」→［関数URLを作成］**。
2. 認証タイプ：**`NONE`** を選ぶ。
   - ⚠️ 不安に感じるかもしれませんが、**中の人（Lambda）が合鍵 `X-Relay-Key` を必ず確認**するので、鍵が無い人は門前払いです。「生の公開」ではありません。
   - なぜ `AWS_IAM` にしないか：munu（classic ASP）に難しい署名処理（SigV4）が必要になり実装困難なためです。
3. CORS：**設定しない（オフのまま）**。munuはサーバ同士の通信でブラウザCORSは関係ないため。
4. **［保存］**。
5. 表示された **関数URL**（`https://XXXX.lambda-url.ap-northeast-1.on.aws/`）を**コピーして保管**。
   - これが `kb_config.asp` の **`RELAY_URL`** になります（末尾のスラッシュ `/` も含めて控える）。

✅ こうなれば成功：関数URLが発行され、`https://….on.aws/` が表示される。

## ステップ7. 動作テスト（鍵つきで叩いてみる）

窓口が正しく反応するか、munuを触る前に確認します。`ALLOWED_IPS` を空にしてある前提です。

### 方法A：AWSの「CloudShell」から（おすすめ・準備不要）

1. コンソール右上の **`>_`（CloudShell）アイコン** をクリック。黒い画面が開く。
2. 次を貼り付け（`<URL>` と `<RELAY_KEY>` を自分の値に）：
   ```bash
   curl -s -X POST "<URL>" \
     -H "Content-Type: application/json" \
     -H "X-Relay-Key: <RELAY_KEY>" \
     -d '{"action":"ask","question":"テスト。これは疎通確認です。","history":""}'
   ```
3. `{"ok":true,"answer":"..."}` のようなJSONが返れば **成功**。

### 確認したい3パターン

| テスト | 送るもの | 期待する結果 |
|---|---|---|
| 正常 | 上のとおり（正しい鍵） | `{"ok":true,...}` |
| 鍵が違う | `X-Relay-Key` をわざと間違える | `{"ok":false,"error":"unauthorized"}`（401） |
| 鍵なし | `X-Relay-Key` ヘッダを付けない | `{"ok":false,"error":"unauthorized"}`（401） |

✅ こうなれば成功：正しい鍵だけ `ok:true`、間違い/無しは `unauthorized`。
これで「合鍵が合う人だけ通る窓口」ができました。

> ❓ `internal_error` や `server_misconfigured` が返る → 環境変数（KB_ID/KB_BUCKET/MODEL_ARN/RELAY_KEY）の設定漏れか、ステップ4の権限不足。
> `CloudWatch`（左メニュー「モニタリング → CloudWatchログを表示」）でエラーの詳細を確認できます。詳しくは `05`。

## ステップ8.（テスト成功後）会社IPで多層防御

munu からの動作まで確認できたら（`02` と `04` のあと）、最後に：

1. Lambda「設定 → 環境変数 → 編集」で **`ALLOWED_IPS`** に会社の公開IPを入れる。
   - 形：`203.0.113.10/32`（`/32` は「このIP1個だけ」の意味）。複数あればカンマ区切り。
   - 🔎 **会社の公開IP（OFFICE_IP）の調べ方**：いま動いている**リレーバケットのバケットポリシー**の中の
     `aws:SourceIp` に入っている値がそれです（S3 → リレーバケット `munu-tacit-relay-…` → 「アクセス許可」→ バケットポリシー）。
     これをコピーするのが最も確実。値が消えていた場合はネットワーク担当に「社内の外向き公開IP」を確認。
   - ⚠️ `whatismyip` 等の自己判定は避ける（社内の出口IPが複数ある場合、自分のPCの見え方と実際の出口が違うことがあるため）。
2. 保存後、munuからもう一度テスト（`05` のチェックリスト）。会社から `ok:true`、社外からは `forbidden` になれば完成。
