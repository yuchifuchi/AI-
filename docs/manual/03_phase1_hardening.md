# 03 Phase 1：応急ハードニング（AWS設定だけ・コード変更なし）

「Route B まではまだ手が回らないが、**今すぐ危険度を下げたい**」ときの応急処置です。
**AWSの設定だけ**で、コードもmunuも触りません。今の（Plan C）構成のまま安全側に寄せます。

> 所要：60分ほど。Route B に進むと、ここでやる一部（`answers/`対策・公開バケット対策）は**不要になって撤去**されます。
> でも「バージョニング」「監査ログ」「コスト上限」は Route B 後も**そのまま活きる**ので、やって損はありません。

対象バケットは2つ：
- **リレーバケット** `munu-tacit-relay-____`（公開・中継用。Route Bで廃止予定）
- **KBバケット** `munu-tacit-kb-____`（非公開・資料の本体）

---

## 1. S3 バージョニングON（削除を「元に戻せる」ようにする）

いまは削除すると復元できません。バージョニングをONにすると、上書き・削除しても前の版が残ります。

**手順（KBバケットとリレーバケットの両方に）**
1. S3 → 対象バケットをクリック → **「プロパティ」タブ**。
2. 「バケットのバージョニング」→ **［編集］** → **「有効にする」** → 保存。

✅ 成功：プロパティに「バージョニング：有効」と表示。
💡 補足：`2. ライフサイクル`と組み合わせ、古い版が無限に溜まらないよう「30日で失効」等も後で足せます。

---

## 2. ライフサイクルで一時ファイルを自動削除（answers/ の残存対策）

`answers/` `incoming/` `questions/` は「一時的な受け渡し」なので、放置せず短時間で消します。
これで「古い回答が残って読まれる」リスクを縮めます。

**手順（リレーバケット）**
1. S3 → リレーバケット → **「管理」タブ** → 「ライフサイクルルール」→ **［ルールを作成］**。
2. ルール名：`expire-transient`。
3. 「ルールスコープ」→ **「プレフィックスでフィルタ」** に `answers/` を指定（1プレフィックスにつき1ルール。`incoming/` `questions/` も同様に**3つ**作る）。
4. アクション：**「オブジェクトの現行バージョンを有効期限切れにする」** にチェック → **1日後**。
5. （バージョニングONなら）「非現行バージョンを完全に削除」→ **1日後** も追加。
6. 作成。

✅ 成功：`answers/` `incoming/` `questions/` に「1日で失効」ルールが3本並ぶ。

---

## 3. `answers/` にトークンを要求（総当り読取を塞ぐ・ポリシー側）

現状 `answers/<reqid>.txt` は**トークン無し**で匿名GETでき、reqidを総当りされると読まれ得ます。
バケットポリシーで `answers/` にもトークンを要求する形にします。

> ⚠️ これは**ポリシー側の準備**です。実際に効かせるにはmunu側も `answers/<TOKEN>/<reqid>.txt` の形で読む改修が必要（依頼書ではPhase 2）。
> **Route B では `answers/` 自体が無くなる**ため、この項目は「Route Bをすぐやるなら省略可」。今のまま延命するなら実施。

考え方：リレーバケットポリシーの「answersを匿名GET許可」している文で、Resource を
`…/answers/*` → `…/answers/<answersトークン>/*` に変更し、munu側の読み取りパスも合わせる。
（この調整は**旧構成の資産**＝AWS上の旧リレーバケットポリシーと、改修前の旧ASP＝git タグ `baseline-plan-c` の
`kb_ask.asp`/`kb_admin.asp` の answers パス生成に依存します。本リポジトリの Route B 版 ASP には `answers/` はありません。
手間の割に効果が半分なので、**基本は Route B 移行を推奨**します）

## 4. 明示 Deny ＋ AWS Config（フェイルオープンの自動見張り）

公開バケットは「IP条件1行を消すと全世界公開」に転落します。これを二重に防ぎます。

**4-1. 明示的な Deny を足す（IP以外は必ず拒否）**
1. S3 → リレーバケット → **「アクセス許可」→ バケットポリシー →［編集］**。
2. 既存の Allow に加えて、**「会社IP以外からのアクセスは Deny」** を1文追加（`aws:SourceIp` の `NotIpAddress` 条件つき Deny）。
   - こうすると、うっかり Allow を広げても Deny が勝つため、全世界公開に落ちにくくなります。
   - ⚠️ 会社の公開IP（OFFICE_IP）を正確に。間違えると自分たちも締め出されます。作業後すぐ疎通確認。

**4-2. AWS Config でドリフト検知**
1. コンソール検索で **`Config`** → 有効化（未設定なら「1-クリックセットアップ」）。
2. マネージドルール **`s3-bucket-public-read-prohibited`** / **`s3-bucket-public-write-prohibited`** を追加。
3. これでバケットが「公開」に変化したら**非準拠として検知**（通知/自動修復も設定可）。

✅ 成功：リレーバケットに Deny文が入り、Config に上記ルールが「準拠(緑)」で並ぶ。

> KBバケットは元々非公開のはず。**「ブロックパブリックアクセス(BPA)＝ON」** になっているか、この機会に確認（S3→KBバケット→アクセス許可→「ブロックパブリックアクセス」がすべてON）。

## 5. CloudTrail データイベント（誰が何を読んだ/消したかの記録）

オブジェクト単位の読み書き・削除を記録し、監査で「いつ・誰が」を追えるようにします。

1. コンソール検索で **`CloudTrail`** → 「証跡」→ **［証跡の作成］**（無ければ）。
2. 証跡名：`munu-s3-data-events`。ログ保存用のS3バケットを新規または既存で指定。
3. **「データイベント」を有効化** → データソース「S3」→ 対象を**リレー／KBの両バケット**に。
   - 読み取り・書き込みの両方を記録。
4. 作成。

✅ 成功：CloudTrailの証跡一覧に `munu-s3-data-events` が「ログ記録：オン」。

> あわせて S3 の **「サーバーアクセスログ」**（プロパティ→サーバーアクセスのログ記録）を、専用のログ用バケットへ出す設定も有効。

## 6. コストを「通知」でなく「実際に止める」

通知だけだと気づくのが遅れます。物理的に止める仕組みを入れます。

**6-1. Lambda 予約同時実行（暴走を頭打ちに）**
1. Lambda → 対象関数 → 「設定 → 同時実行 →［編集］」→ **予約された同時実行数＝5**。

**6-2. AWS Budgets ＋ Budget Action**
1. コンソール検索で **`Budgets`** → **［予算を作成］** → 月額（例 `$40`）。
2. **「予算アクション」** を設定：しきい値超過時に、あらかじめ用意した**制限用IAMポリシーをアタッチ**して支出を止める、等。
   - まずは通知（メール）だけでも可。可能なら Action まで。

✅ 成功：Lambda に「予約同時実行 5」、Budgets に月$40の予算（できればアクション付き）。
