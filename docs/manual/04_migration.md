# 04 移行手順（旧→新へ、止めずに切り替える）

いま動いている旧方式（Plan C・公開S3）を止めずに、Route B（鍵つき窓口）へ切り替えます。
**いつでも元に戻せる**やり方で進めます。

> 考え方：**新しい窓口を横に作って（旧は動いたまま）→ テスト用フォルダで確認 → 一瞬で差し替え → 数日見守り → 旧を撤去**。
> 差し替えの瞬間だけ数秒。問題があれば**バックアップに戻すだけ**で復旧できます。

---

## 全体の流れ（5フェーズ）

```
A. 新窓口を作る（旧は無傷）        … 01のAWS設定。ユーザー影響ゼロ
B. テスト用フォルダで確認          … tacit2test/ に新ASPを置いて検証。本番tacit2/は無傷
C. 差し替え（唯一の切替）          … tacit2/ をバックアップ→新ASPで上書き。数秒
D. 見守り（数日）                  … 監査ログ・エラーを確認
E. 旧を撤去＋バケットを非公開化     … 公開バケット廃止・BPA ON・旧Lambda停止
```

---

## フェーズA. 新窓口を作る（ユーザー影響なし）

- `01_aws_setup.md` を最後まで実施し、**Function URL（RELAY_URL）** と **合鍵** を用意する。
- このとき **`ALLOWED_IPS` は空**のまま（テストのため）。
- 旧方式（旧Lambda・公開バケット・旧ASP）は**一切触らない**。ユーザーは今までどおり使えます。

✅ Aのゴール：CloudShellテスト（`01`ステップ7）で新窓口が `ok:true` を返す。

---

## フェーズB. テスト用フォルダで確認（本番はまだ無傷）

本番の `tacit2/` を触る前に、コピーの `tacit2test/` で新ASPを検証します。

1. munu に **`…/tacit2test/`** フォルダを作る。
2. そこへ、`02_munu_install.md` のとおり**新ASP5ファイル**を置く：
   - `kb_config.asp`（本物・RELAY_URL/RELAY_KEY/ADMIN_OP_KEY 入り）／`kb_lib.asp`／`kb_register.asp`／`kb_ask.asp`／`kb_admin.asp`
3. ブラウザで `http://www.hanbai.mint.go.jp/tacit2test/kb_ask.asp` 等を開き、**登録・質問・管理の3つ**を確認（`02`ステップ4）。
   - このとき登録テストをすると本番KBに1件入ります。確認後、管理画面で削除しておくと綺麗です。

✅ Bのゴール：`tacit2test/` で3画面すべてが正常。旧 `tacit2/` は今までどおり動いている。

> 💡 ポイント：AとBの間、**旧と新が並走**します（旧＝公開S3経由、新＝Function URL経由）。KBは共通なので、登録も検索も両方から使えます。これが「無停止」の肝です。

---

## フェーズC. 差し替え（唯一の切り替え・数秒）

`tacit2test/` で問題なしを確認できたら、本番 `tacit2/` を新方式にします。

1. **バックアップ**：本番 `tacit2/` の中身を丸ごと `tacit2_backup_YYYYMMDD/` にコピー（**必ず**。戻すときに使う）。
   - 特に旧 `kb_config.asp`（旧トークン入り）も控える。
2. **上書き**：`tacit2test/` の5ファイル（新ASP＋新 `kb_config.asp`）を `tacit2/` に上書きコピー。
3. **即テスト**：`http://www.hanbai.mint.go.jp/tacit2/kb_ask.asp` で1問。回答が返れば切替成功。
4. `01`ステップ8にしたがって、Lambda の **`ALLOWED_IPS` に会社の公開IP** を入れる（多層防御ON）。入れたら本番からもう一度疎通確認。

✅ Cのゴール：本番 `tacit2/` が新方式（Function URL）で動く。会社から `ok`、社外から `forbidden`。

### 🔙 切り戻し（うまくいかないとき）
- `tacit2_backup_YYYYMMDD/` の中身を `tacit2/` に戻すだけ。旧 `kb_config.asp`（旧トークン）も戻す。
- 旧方式の公開バケット・旧LambdaはフェーズEまで生かしてあるので、戻せば即復旧します。
- あわてて次のフェーズEに進まないこと（旧を消す前に数日様子を見る）。

---

## フェーズD. 見守り（2〜3日）

- CloudWatch（Lambda `munu-kb-routeb` のログ）で、`register`/`ask`/`admin` の監査ログが出ているか、`internal_error` が頻発していないかを確認。
- ユーザーに「登録・質問・管理が普段どおりか」を確認。
- 問題があればフェーズCの切り戻しで即対応。

✅ Dのゴール：数日、エラーなく回っている。

---

## フェーズE. 旧を撤去＋バケットを非公開化（仕上げ・ここが本丸）

新方式が安定したら、**危険だった公開バケットを潰し、KBバケットを固くロック**します。ここまでやって Route B 完成です。

> ⚠️ ここは**後戻りしにくい**操作を含みます。フェーズC/Dで新方式が安定していることを必ず確認してから。

### E-1. 旧S3リレーの停止
1. 旧Lambda（`munu-kb-relay`）の **S3トリガーを無効化/削除**（新方式はこのLambdaを使わない）。
2. 旧Lambda自体は、しばらく残して**無効化**でも可（完全削除は最後に）。

### E-2. ★KBバケットを「非公開の固定ロック」に（BPA ON）※最重要
> **バケットポリシーだけでは非公開になりません。** 「ブロックパブリックアクセス(BPA)」を必ずONにします。
1. S3 → **KBバケット** → 「アクセス許可」→ **「ブロックパブリックアクセス」→［編集］** → **4項目すべてON** → 保存（`確認`を入力）。
2. 同じ「アクセス許可 → バケットポリシー →［編集］」で、`aws/s3_kb_bucket_policy_routeb.json` を貼り付け、
   - `KB_BUCKET_NAME` を実バケット名に、`ACCOUNT_ID` を `262504054116` に**全置換** → 保存。
   - 効果：**非TLS通信を拒否**＋**アカウント外からのアクセスを拒否**。匿名アクセスは元から不可に。
3. 疎通確認：新方式で質問して**まだ回答が返る**こと（Lambda実行ロールはBPA/ポリシーの影響を受けず読める）。

✅ E-2のゴール：KBバケットのBPAが全ON、バケットポリシーにDeny2本。質問は正常。

### E-3. 公開リレーバケットの廃止
1. リレーバケットは新方式では**未使用**。中身（`answers/` `incoming/` `questions/`）をライフサイクルで空にしてから、
2. バケットの**公開バケットポリシーを削除**（`Principal:"*"` の Allow を消す）。
3. 十分な待機期間（数日）を置き、参照が無いことを確認できたら**バケットごと削除**。
   - ※急がなくてOK。まず「公開ポリシー削除」で公開を止め、削除は後日でも可。

### E-4. 旧ファイルの掃除（引き継ぎ資料11章）
- munu から `aws_*.asp`（API Gateway版）・`test_*.asp`（到達テスト・プロキシ情報が見える）を削除。
- `tacit2test/` も役目を終えたら削除（`kb_config.asp` が残らないように）。

### E-5. セッションCookieの堅牢化（管理UIの守り・任意だが推奨）
- IISで、`tacit2/` のセッションCookieを **HttpOnly**（＋HTTPS化後は **Secure**）に、`Session.Timeout` を短め（例20分）に。
- 理由：管理opの認可は鍵で守れますが、UI経由の「セッション偽造」への守りはCookieの堅牢性が担うため（`05` 参照）。

---

## 移行完了チェック

- [ ] A: 新Function URLがCloudShellテストで通る
- [ ] B: `tacit2test/` で3画面が正常（旧は無傷で並走）
- [ ] C: `tacit2/` を新方式に差し替え、バックアップも確保、`ALLOWED_IPS`設定
- [ ] D: 2〜3日エラーなく稼働
- [ ] E-1: 旧LambdaのS3トリガー無効化
- [ ] **E-2: KBバケット BPA=ON ＋ 非公開バケットポリシー適用（最重要）**
- [ ] E-3: 公開リレーバケットの公開ポリシー削除（後日バケット削除）
- [ ] E-4: 旧ASP（aws_*/test_*）と tacit2test/ を掃除
- [ ] E-5: 管理UIセッションCookie堅牢化（推奨）

ここまでで、診断が「不適格」とした**公開S3・匿名アクセス・管理認可の飾り**が構造的に解消され、
**監査ログ・非公開バケット・鍵つき窓口**の状態になります。残る HTTPS化・秘密の平文集約は Phase 3/運用で。
